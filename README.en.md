## Why the Image Was Interlacing or Throwing Errors

The root cause of the interlacing was not the display server (Wayland vs X11), but
the **USB 2.0 bus bandwidth limit**.

### 1. The USB 2.0 Bus Cannot Handle 60 Hz at 1440×900

The alternative **ms912x driver (by jcrobles)** attempted to deliver every frame
at the *nominal* rate of 60 Hz. However, a single full frame of 1440×900 in RGB888
is ~3.9 MB; at the actual USB 2.0 throughput (~40 MB/s), that cap is ~19 Hz max.
As a result, each frame arrived late: **the display panel was already scanning when
the next frame arrived** → causing tearing, interlacing, and instability.

The display server plays no role here: both Wayland and X11 compose the image
and hand it over to the kernel driver, which pushes it over the same USB cable
to the same chip. Switching display servers does not alter the physical transport.

### 2. Transport Solution: YUV422 Blocks (Windows Driver Style)

The official Windows driver does not transmit full frames; instead, it sends **only
the modified region** (dirty-rects) in **YUV422 format (2 bytes/px)** with a block
header. This drastically reduces the data payload, allowing the real refresh rate
to increase from ~19 Hz to **~30 Hz**.

In this patch, this transport mechanism is enabled via `block_transfer=1` (`usbdisp_usb`
module). Each frame is split into pixel blocks, and only updated blocks travel
across the wire. This keeps the image stable and tear-free, as each frame arrives on time.

> Previously, this transport method was dismissed due to a "broken image" issue.
> However, that was caused by a missing video mode (VGA patch) rather than the
> transport mechanism itself. With the VGA patch applied + `block_transfer=1`,
> the image is rock-solid.

## How the Functional Cursor Was Achieved

The hardware chip **lacks a hardware cursor overlay**; the cursor must be rendered
via software inside the framebuffer. In GNOME/Wayland multi-GPU setups (Intel iGPU +
USB GPU), Mutter suppressed the cursor on the USB monitor because it assumed the
primary GPU's hardware cursor covered all displays.

### The Solution: Force Mutter's Software Cursor

Add the following environment variable to `/etc/environment`:

```bash
MUTTER_DEBUG_DISABLE_HW_CURSORS=1
```

This instructs **Mutter to render the cursor via software directly onto each
framebuffer**. Since that framebuffer is sent over USB to the adapter, the cursor
appears accurately and smoothly.

> This is a **compositor-level tweak (Mutter)**, not a kernel driver change.
> This makes it fully compatible with the 30 Hz driver: both seamlessly combine —
> a stable 30 Hz display driver + Mutter-rendered software cursor.

## Resolution Selection: Safe & Crash-Free

Changing resolutions **on the fly** from GNOME's *Settings > Displays* causes a
kernel crash on this USB monitor: the driver initiates a modeset while the KMS
thread is still copying the previous framebuffer (use-after-free → page fault →
gray screen).

The solution operates at two levels and is fully automated by `MENU` and
`cambiar-resolucion.sh`:

1. **Driver Preferred Mode (`pref_w`/`pref_h`).** The driver constructs its
   PREFERRED mode using these module parameters at boot (default: 800×600).
   GNOME adopts this mode upon logging in **without triggering a live modeset**,
   completely preventing the use-after-free crash. The configuration is persisted in
   `/etc/modprobe.d/msdisp-pref.conf`:

   ```
   options usbdisp_drm pref_w=1280 pref_h=1024
   ```

2. **Real Refresh Rate.** CVT modes generated by the driver use fractional rates
   (e.g., 59.96 or 74.98 Hz, not exact 60 Hz). GNOME discards `monitors.xml` if
   the saved refresh rate does not match the mode exactly. Therefore,
   `cambiar-resolucion.sh` extracts the exact rate using `modetest` (refresh =
   clock×1000/(htot×vtot)) with a static lookup table backup, and writes the
   exact value into `monitors.xml`.

## Applied Persistent Configurations

| File | Content | Effect |
| :--- | :--- | :--- |
| `/etc/modprobe.d/blacklist-ms912x.conf` | `blacklist ms912x` | Prevents the jcrobles driver from binding |
| `/etc/modprobe.d/msdisp-block.conf` | `options usbdisp_usb block_transfer=1` | Enables 30 Hz mode (YUV422 blocks) |
| `/etc/modprobe.d/msdisp-pref.conf` | `options usbdisp_drm pref_w=... pref_h=...` | Sets USB monitor boot resolution |
| `/etc/environment` | `MUTTER_DEBUG_DISABLE_HW_CURSORS=1` | Forces software cursor rendering |

### Freeze-Free Reboot (Optional but Recommended)

In multi-GPU systems (iGPU + NVIDIA + USB adapter), Plymouth may hang while drawing
the shutdown animation on an unbinding adapter. The system will eventually reboot
after systemd timeouts, but it appears frozen. To bypass Plymouth during reboots:

```bash
sudo systemctl mask plymouth-reboot.service plymouth-quit-wait.service
```

Live status verification commands:

```bash
# Check transport mode (Y = 30Hz blocks, N = full frame)
cat /sys/module/usbdisp_usb/parameters/block_transfer

# Check DRM module preferred mode parameters
cat /sys/module/usbdisp_drm/parameters/pref_w
cat /sys/module/usbdisp_drm/parameters/pref_h

# Inspect active pipeline status (pipeline0) and frame stats
cat /sys/devices/usbevdi/msdisp_plat.0/pipeline0/info
cat /sys/devices/usbevdi/msdisp_plat.0/pipeline0/frame
```

## Installation

### Prerequisites

- Arch Linux / CachyOS - GNOME.
- System dependencies: `sudo pacman -S dkms base-devel linux-headers`

### Installation Steps

```bash
sudo bash install.sh
sudo reboot
```

`install.sh` copies the source code to `/usr/src`, compiles and installs via DKMS,
applies persistent configuration files, and reloads kernel modules.
At step 7/7, it prompts you to run `MENU` to pick your preferred resolution **before
the first reboot** — ensuring your display turns on immediately at startup without a
black screen. A system reboot is required as kernel modules cannot be fully reloaded live.

## Changing Resolutions Safely (CLI / Crash-Free)

```bash
# Interactive menu: lists supported modes with exact refresh rates
# (detected via modetest) and reboots with the selection applied
sudo ./MENU

# Command line tool (used by MENU): sets resolution and reboots
sudo ./cambiar-resolucion.sh 1280 1024         # auto-detects real refresh rate
sudo ./cambiar-resolucion.sh 800 600 59.96     # or explicitly specify rate
```

`MENU` dynamically parses connector modes (from 640×480 up to 1920×1080, excluding
1366×768 which the hardware driver does not expose) along with their true refresh rates,
making it compatible with any monitor (60 Hz, 75 Hz, etc.). If `modetest` is missing, it
falls back to a static table.

How resolution switching works:
1. Updates `/etc/modprobe.d/msdisp-pref.conf` so the driver boots with the requested mode as PREFERRED (no live modeset → no gray screen crash).
2. Creates a backup of `monitors.xml` (`.bak-res`) and updates the USB monitor entry with the exact refresh rate.
3. Re-arranges display layout per row so Mutter doesn't reject the file (`Logical monitors not adjacent`).
4. Reboots the system.

Lower resolution = fewer MB per frame across the USB 2.0 bus = higher actual frame rate.

## Uninstallation / Rollback

To completely remove the driver and restore system defaults:

```bash
sudo rm -f /etc/modprobe.d/blacklist-ms912x.conf
sudo rm -f /etc/modprobe.d/msdisp-block.conf
sudo rm -f /etc/modprobe.d/msdisp-pref.conf
sudo dkms remove -m msdisp-drm -v 3.0.3.12 --all
sudo sed -i '/MUTTER_DEBUG_DISABLE_HW_CURSORS/d' /etc/environment
sudo systemctl unmask plymouth-reboot.service plymouth-quit-wait.service 2>/dev/null
sudo reboot
```
